# onboarding.md — オンボーディングフロー詳細設計

**ステータス**: 確定(2026-07-16)
**対応FR**: FR-14
**関連**: character-window.md、model-mapping-ui.md、api.md 1章、要件定義書 C-08・C-16・C-19

## 背景

4ステップ(ようこそ画面→モデルインポート誘導→モード選択→完了)までは確定しているが、各画面の詳細は未確定。

## 結論

| 論点 | 決定 |
|---|---|
| ようこそ画面 | UIの語彙(憑坐・霊力状態)を読める最小限だけ教える。**スキップ可** |
| モデルインポート | **必須にしない**(生成フローがアプリの外に出るため、そもそも一続きで完了できない) |
| モード選択の初期値 | **Code Adapter**。ただし**同ステップでhooks設定を提示する** |
| 完了画面 | 設定が済んでいない項目について**嘘をつかない**。メニューバーアイコンを必ず教える |

**貫く原則**: オンボーディングは**一度も行き止まりを作らず、未完了の項目について嘘をつかない**。

## 検討ログ

### 論点2から先に答える: モデルインポートは必須にできない

論点2は「この画面でモデルを未設定のままスキップできるか、必須にするか」と問うている。**必須にできない。** これは好みの問題ではなく、フローの構造上の帰結である。

要件定義書4.5が定めるスプライトセットの追加フローを見ると:

1. 静止画1枚をアップロード
2. アプリがクロマグリーン合成画像を生成
3. **ユーザーがその画像を外部の動画生成AIサービス(Pika・Canva等)に渡して動画を生成**
4. 生成された動画をアプリに取り込む

**手順3でユーザーはアプリの外に出る。** 別のWebサービスでアカウントを作り、画像をアップし、生成を待ち、ダウンロードする。感情ごとに繰り返す。これは数分から数時間かかる作業であり、**オンボーディングの1画面で一続きに完了できる性質のものではない**。

モデルインポートを必須にすると、初回起動時のユーザーは外部サービスでの作業を終えるまでオンボーディングを抜けられない。アプリを閉じて出直すことになり、次に起動したときまたオンボーディングが始まる。行き止まりである。

Live2D形式(フォルダ/zipドロップ)なら一続きで完了しうるが、C-16が**Live2Dを上級者向け**と位置づけている以上、初回のユーザーが手元にLive2Dモデルを持っている前提は置けない。

加えて、**モデル0体はUI上の正当な状態**である。モックアップのモデル管理タブは「モデルがまだありません。上の『追加するモデルの形式』から追加してください。」を表示するよう既に作られている(control-panel.jsx L771)。0体は異常系ではない。

したがって**この画面の役割は「導線を見せること」であって「完了させること」ではない**。スプライトセットが標準の入口であることを伝え、Control Panelのモデル管理タブへ送り、後から続きをやれると明示する。

### 論点3: モード選択

#### 発見した問題: Code Adapterを選んでも動かない

**このステップには穴がある。** モード選択でCode Adapterを選ばせても、それだけでは**キャラクターは永久に無反応のまま**である。

FR-2が定めるCode Adapterの通信方式は「hooksスクリプト(`dispatch.sh`) → ローカルサーバー」であり、動作させるにはユーザー側で以下が必要になる。

1. `dispatch.sh`を自分のプロジェクトに配置する
2. 自分のプロジェクトの`.claude/settings.json`にhooks設定を書く(テンプレートはapi.md 1.2にある)
3. `codeAdapter.watchedProjectPaths`を設定する

**4ステップのオンボーディングはこのどれにも触れていない。** つまり現状の設計どおりに実装すると、ユーザーはモード選択でCodeを選び、完了画面を見て、キャラクターが出てきて、**何も起きない**。ユーザーから見ればアプリが壊れている。オンボーディングの目的が「使える状態にすること」だとすれば、この4ステップはその目的を達成していない。

#### 決定: hooks設定を同ステップに畳み込む

5ステップ目を足すとFR-14の「4ステップ」という確定事項の変更(=Notion正本の更新)を伴う。**モード選択ステップの中に畳み込む**ことで、構成を変えずに穴を塞ぐ。

Code Adapterを選択したときだけ、同じ画面に以下を展開する。

- **監視するプロジェクトを選ぶ**(ネイティブのディレクトリ選択 → `watchedProjectPaths`へ)
- **`dispatch.sh`をそのプロジェクトへ配置するボタン**(アプリが書き込む。手作業でのコピーを要求しない)
- **`.claude/settings.json`に追記するJSON**(api.md 1.2のテンプレート。コピーボタン付き)
- **「あとで設定する」**

`.claude/settings.json`はユーザーの既存ファイルであり、既にhooksが設定されている可能性がある。**アプリが勝手に上書きしてはならない**ので、書き込みではなくコピー用の提示に留める。`dispatch.sh`は新規ファイルなので配置してよい。

> **注意(実装時)**: ここで扱う`.claude/settings.json`は**アプリの利用者側のプロジェクト**のものであり、このリポジトリ自身の開発用hooksとは別物である(CLAUDE.md・api.md 1.2の注記参照)。混同するとオンボーディングのコードが自分のリポジトリを書き換えかねない。

#### 初期値: Code Adapter

論点は「Code Adapter / Chat Adapterのどちらを初期値にするか」。**Codeを初期値にする。**

- 要件定義書1章はこのアプリを「**Claude Codeでの作業実況**と、Claudeとのチャット対話を...伴走する」と定義し、作業実況を先に挙げている。2章も「開発者自身のClaude Code活用基盤(ハーネスエンジニアリング)の一環」と位置づける。**アプリの存在理由がCode側にある。**
- Chatを初期値にすると、このアプリをClaude Codeの実況のために入れたユーザーが、結局あとから自分でCodeへ切り替えることになる。

**Chat + mockならセットアップ0で即座に動く**(C-08により既定はmock、課金なし)ため、「まず動くものを見たい」を初期値にする案も成立する。しかしそれは**アプリの主目的を既定から外す**ことと引き換えになる。上記のhooks設定を同ステップに畳み込めば、Codeを選んでも行き止まりにならないので、主目的を既定に置ける。

FR-1によりアダプタ切替はControl Panelのホーム画面からいつでもできる。初期値は入口であって固定ではない旨を画面に明記する(論点3の「『後で変更できる』旨をどう伝えるか」への回答)。

> **要確認**: `activeAdapter`は**スキーマ上の既定値を持たない必須フィールド**である(data.md 1章 / config-schema.ts)。現在`createDefaultConfig()`が`'code'`を決め打ちしているが、これはスキャフォールド作成時の暫定であり、本ドキュメントの決定によって追認された形になる。スキーマに`.default('code')`を持たせるかは、オンボーディングが必ず値を書き込む以上どちらでもよい。

### 論点1: ようこそ画面

#### キャラクター紹介は「UIを読めるようになる」最小限に留める

論点は「名前・世界観をどこまで説明するか」。**UIに実際に出てくる語彙を読める分だけ**とする。

モックアップの憑坐状態帯には、常時こう表示されている(control-panel.jsx L379-385)。

```
憑坐: 常世灯里(とこよ あかり)
霊力状態 ── 静穏(せいおん)
```

つまり**「憑坐」「霊力状態」「静穏/昂揚/減衰」という語彙を知らないとUIが読めない**。ようこそ画面の実用的な役割はここにある。世界観の読み物を書くことではなく、この3語を通じさせること。

- **常世灯里(とこよ あかり)** — このアプリに宿るキャラクターの名前
- **憑坐(よりまし)** — 灯里の役どころ。あなたの作業に憑いて、代わりに反応する存在
- **霊力状態** — 灯里の今の気分(Mood)。作業の調子に応じて 静穏 → 昂揚 / 減衰 と移る

デザイン方向性が電脳オカルト×HUDである以上、この語彙自体が体験の一部である。ただしオンボーディングで世界観を語り込むのは、**アプリを使い始めたい人の前に立ちはだかる読み物**になる。上記3点を1画面に収める。

#### スキップ可能にする

**可能にする。** ようこそ画面は紹介であって設定ではない。読みたくない人を足止めする理由がない。

スキップは**完了画面へ直行**する。これが成立するのは、後続2ステップのどちらも必須ではないため。

- モデルインポート: 前述のとおり必須にできない(0体は正当な状態)
- モード選択: 初期値(Code)がある

つまり**オンボーディング全体が実質スキップ可能**である。これは欠陥ではなく、前述の原則の帰結——一度も行き止まりを作らない——である。ただし**スキップした結果どうなるかについては嘘をつかない**(論点4)。

### 論点4: 完了画面

論点は「完了後、実際にキャラクターウィンドウが表示されるまでの遷移演出」。演出より先に決めるべきことが2つある。

#### 1. モデルが0体なら、キャラクターウィンドウを開かない

モデル未設定のまま完了した場合、キャラクターウィンドウを開いても**描くものが無い**。透過・枠なしのウィンドウなので、開いても**画面上に何も見えない**。ユーザーからは「完了したのに何も起きなかった」としか見えず、アプリが壊れたと判断される。

したがって:

| モデル | 完了時の挙動 |
|---|---|
| 1体以上 | キャラクターウィンドウを開く(character-window.mdの初期配置=プライマリのworkArea右下) |
| 0体 | **開かない**。「モデルを追加すると灯里が現れます」と伝え、Control Panelのモデル管理タブへ送る |

#### 2. メニューバーアイコンを必ず教える

**これが完了画面の最も重要な役割である。**

`general.clickThrough`の既定は`true`である。つまり**初回起動時、キャラクターウィンドウはマウスイベントを一切受け取らない**。ユーザーが灯里をクリックしても、ドラッグしようとしても、右クリックしても、何も起きない。裏のウィンドウが反応するだけである。

C-19でメニューバーアイコンを常設すると決めたのは、まさにこの行き止まりを塞ぐためだった(character-window.md 論点3)。**その存在をユーザーが知らなければ、対策として機能しない。**

完了画面で必ず伝える。

- 灯里はクリックを通り抜けます(裏のウィンドウがそのまま操作できます)
- **操作はメニューバーのアイコンから**(位置を図示する)
- クリックスルーを切ればドラッグで動かせます

#### 3. 未完了の項目について嘘をつかない

スキップされうる項目があるため、完了画面は**実際に何が設定され、何が残っているか**を示す。「セットアップ完了!」とだけ出して、実際にはhooksが未設定でキャラクターが無反応、という状態を作らない。

| 状態 | 完了画面の表示 |
|---|---|
| モデル0体 | 「モデルを追加すると灯里が現れます」→ モデル管理タブへ |
| Code選択 + hooks未設定 | 「hooksの設定が終わるまで、灯里はClaude Codeの作業に反応しません」→ 設定手順へ |
| Chat + mock | 「今はモック(固定返答)で動いています。実際にClaudeと話すにはAPIキーの設定が必要です」 |
| すべて設定済み | 「準備ができました」 |

これはchat-adapter-errors.mdでmockへの自動フォールバックを退けたのと同じ理由による。**アプリが自分の状態について嘘をつかない。**

#### 遷移演出

上記を満たした上での演出。モックアップが既に持っている表現を流用し、新しい語彙を持ち込まない。

- 完了ボタン → 憑坐状態帯の**呪紋(魔法陣)リングが一度強く回転**し、`m.glow`のブルームが膨らむ(control-panel.jsx L324-352の`seal-spin` / `breathe`アニメーションのパラメータを一時的に強める)
- 収まると同時にキャラクターウィンドウがフェードインする(灯里が「降りてくる」表現)
- Control Panelはホームタブへ遷移する

憑坐に霊が降りるという世界観と、実際にウィンドウが出現する動作が一致する。既存のシグネチャモーション(basic-design.md 4.3)を使うため、この演出のために新しいアセットは要らない。

### 形式による分岐について

オンボーディングは**Live2Dとスプライトセットのどちらにも依存しない**。モデルインポート誘導で両形式を提示する(C-16に従いスプライトセットを既定・おすすめとして先に置く)が、これはモックアップの「追加するモデルの形式」セクション(control-panel.jsx L606-648)がすでに実装している選択UIであり、オンボーディングはそこへ送るだけである。取り込み処理そのものはmodel-mapping-ui.mdとspriteset-pipeline.mdの管轄で、本ドキュメントで形式ごとの分岐は発生しない。
