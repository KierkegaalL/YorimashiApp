**ステータス**: 確定(2026-07-17)。2026-07-18に入力欄まわりの機能(C-23)を追加し、残していた「実装前に決着が必要な事項」2件(論点5=`activeAdapter`との関係、折りたたみ状態の保存先)を決着。同日、**折りたたみ対象を会話ペインからControl Panel側に変更**(仕様変更、C-21改定)、**折りたたみ時にウィンドウ全体を会話ペイン幅まで縮小する方式に決定**し、モックアップ(control-panel.jsx)へ2ペイン構成+入力欄機能(C-23)を実装済み

## 背景

FR-3（Chat Adapter）は動作モード・感情判定・APIキー保存までは決まっていたが、**ユーザーがどこでメッセージを打ち、Claudeの応答をどこで読むのかが要件レベルで一切定義されていなかった**。lipsync.md は「テキストが画面に流れ続けている」「streaming表示のUI」と書きながら、その表示先の画面自体を一度も定義していない。この欠落を埋めるためFR-15を新設した。

## 結論

| 論点 | 決定 |
|---|---|
| 配置 | **Control Panelと同一ウィンドウ内の左ペイン**。別ウィンドウにしない（C-21） |
| 既定状態 | 会話ペイン・Control Panel の**両方が展開** |
| 折りたたみ | ペインの縁にあるタブ（つまみ）で**Control Panel側のみ**折りたたむ。会話ペインは常時表示で畳めない（2026-07-18仕様変更） |
| 会話履歴 | **v1では永続化しない**（メモリのみ）（C-22） |
| streaming | 受信チャンクを逐次追記。**mockも擬似streamingで流す**（lipsync.md） |
| 感情の発火 | 送信時に`thinking`（sustain付き）、受信完了時に`classify()`（emotion-classification.md） |
| 入力欄の機能 | **スラッシュ / @参照 / 添付(real) / 応答モデル選択(real) / 停止 / コンテキスト表示 / メッセージ操作 / 入力ヒント**（C-23。後述の専用節） |
| 送信時のアダプタ | **`activeAdapter`をChatへ自動切替 + 明示**（案1・C-24。論点5決着） |
| 折りたたみ状態 | `config.general.controlPanelCollapsed`（default `false`）に保存（要決着だった保存先を決定） |

## 検討ログ

### 論点1: レイアウトと折りたたみ

#### 構成

```
┌─ Control Panel ウィンドウ（1つ） ─────────────────────┐
│ ┌── 会話ペイン ───────┐ ┃ ┌── Control Panel ─────┐ │
│ │ 憑坐状態帯           │ ┃ │ タブバー(6タブ)       │ │
│ │  呪紋リング + Mood   │ ┃ ├─────────────────┤ │
│ ├──────────────┤ ┃ │                     │ │
│ │                    │ ┃ │  各タブの内容          │ │
│ │  会話履歴（スクロール）│ ┃ │  (400px固定)        │ │
│ │   ユーザー発話        │ ┃ │                     │ │
│ │   灯里の応答          │ ┃ │                     │ │
│ │   (streaming)       │ ┃ │                     │ │
│ │                    │ ┃ │                     │ │
│ ├──────────────┤ ┃ │                     │ │
│ │ [入力欄]      [送信] │ ┃ │                     │ │
│ └──────────────┘ ┃ └─────────────────┘ │
│                     ▲                              │
│                  折りたたみタブ                       │
└──────────────────────────────────────────┘
```

**憑坐状態帯を会話ペインの先頭に置く。** モックアップ（control-panel.jsx L318-397）が既に持っている呪紋リング+Mood表示をそのまま流用する。会話中は灯里の表情がキャラクターウィンドウ側にしか出ないため、**Control Panelを見ているユーザーには灯里の状態が見えない**。会話ペインに状態帯があれば、視線を動かさずに`thinking`/`happy`/`panic`が読める。新しいアセットも新しい語彙も要らない。

#### 折りたたみはControl Panel側のみ（縁のタブ。2026-07-18仕様変更）

会話ペイン側は畳めない。**畳めるものが2つあると「両方畳んだら何も残らない」状態を作れてしまう**。Control Panelだけを畳める非対称にすることで、ウィンドウが空になる経路が生まれない。

> 当初はこの逆（会話ペインのみ畳める）で確定していたが、2026-07-18に折りたたみ対象を反転した。会話ペインを常時表示の主画面とし、設定を使わない間はControl Panel側を隠して会話に画面を使う運用に変更している。

折りたたみ状態は`config.general`に保存する（後述の要決着事項）。

#### ウィンドウ幅の配分とリサイズ（2026-07-18仕様追加）

**折りたたみは内部レイアウトの再フローではなく、Control Panelウィンドウ(Electron `BrowserWindow`)自体の幅を会話ペインの幅まで縮小する。** Control Panel側を畳んだとき、単に中身を隠して1000px幅の窓に空白を残すのではなく、ウィンドウの外形そのものが会話ペインぶんの幅まで縮む。ユーザーの指示（「折りたたむ際にウィンドウ全体を会話画面の大きさに合わせて縮小する」）による決定。

| 領域 | 幅 |
|---|---|
| 会話ペイン | 可変（残り全部）。目安 560px |
| 折りたたみタブ | 約 16px |
| Control Panel | 展開時 **400px 固定**（モックアップの`width:400`固定に合わせる） |
| **ウィンドウ全体** | **展開時 976px(560+16+400) / 折りたたみ時 576px(560+16)** |

現在のControl Panelウィンドウの既定値は`1000 × 720`（`src/main/index.ts`）。976pxとの差は実装時に埋める（角丸・枠線ぶんの誤差か、既定値自体を976に合わせるかは実機で確認する。TODO参照）。

> **実装時の注意（Main側）**: `BrowserWindow.setBounds()`で幅のみを変更し、高さ・左上の位置(`x, y`)は固定する（右辺だけが動くようにし、ウィンドウが画面上で飛ばないようにする）。次回起動時は`config.general.controlPanelCollapsed`の保存値に応じて、生成時点から折りたたみ幅でウィンドウを作る（開いてからリサイズするより自然）。アニメーションさせるかどうかは別論点（実装TODO参照）。

**モックアップへの反映（2026-07-18・実装済み）**: `docs/mockups/control-panel.jsx`の最外殻を2ペイン構成に書き換えた。`Section`/`Row`/`THEMES`には手を入れず、外側のflexレイアウトのみ変更している。折りたたみトグルで外側コンテナのwidthを976px⇄576pxでアニメーションさせ、「ウィンドウ全体が縮小する」動きをReactコンポーネントレベルで再現している（esbuildでバンドルしブラウザ上で実描画し、折りたたみ/展開の往復・送信/停止トグル・スラッシュメニュー・realモード切替時の添付/モデル選択/コンテキスト表示の有効化を確認済み。**ただしこれはブラウザでのReactコンポーネント検証であり、Electronアプリ本体の動作確認ではない**。実際の`BrowserWindow`リサイズはMainプロセス実装時に別途必要）。

### 論点2: 会話履歴を永続化しない（C-22）

**メモリのみ。ウィンドウを閉じたら消える。**

要件定義書8章は「ランタイムデータ（hooksログ・**チャット履歴**）は送らない」と**チャット履歴の存在を前提にしている**が、リポジトリ全体を探しても**保存先の定義がどこにもない**。`config.json`にも`userData`配下のディレクトリ構成（data.md 3章）にも無い。

対して hooksログは C-03 で「**7日で自動削除**、パーミッション0600、ファイルパスも含めて保存（デバッグ優先）」と**明示的に決めている**。チャット履歴は hooksログより機微（会話内容そのもの）でありながら、保持期間・パーミッション・削除UI・エクスポート時のマスクのどれも決まっていない。

**何も決まっていない状態で永続化を始めると、最も機微なデータが最も無管理に溜まる。** v1は永続化しない。

補強する事情:
- 既定モードは`mock`（C-08）。v1の会話の大半は固定返答であり、永続化の価値が低い。
- 要件定義書10章のスコープ外に「クラウド同期（config/ログの端末間同期）」はあるが、チャット履歴の永続化は要件に一度も現れない。

永続化する場合に決めるべきことは C-03 と同型（保持期間・パーミッション・削除導線・エクスポート時のマスク方針）。**それを決めてから実装する**。

### 論点3: 送信から表示までの経路

既存の詳細設計が決めた内容を組み立てるだけで、新しい判断はほとんど無い。

```
[送信ボタン / Enter]
  ↓
engine.trigger('thinking', { sustain: true })   ← lipsync.md
  ↓
Renderer → IPC → Main（Chat Adapter）
  ↓
mock: 固定返答を擬似streamingで流す ┐          ← lipsync.md
real: SDK の messages.stream()    ┘          ← chat-adapter-errors.md
  ↓  （無通信ウォッチドッグ付き。SDKのtimeoutは凍ったstreamに効かない）
Main → IPC → Renderer へチャンクを逐次送出
  ↓
会話ペインの最後の吹き出しに追記（streaming表示）
  ↓
[受信完了]
  ↓
engine.release('thinking')                     ← lipsync.md
classify(応答テキスト全文) → trigger(state)      ← emotion-classification.md
```

**`release()`の呼び忘れは`thinking`の永久固着を招く**（lipsync.md）。成功・失敗・中断・無通信タイムアウトの**すべての経路**で`release()`が呼ばれることを実装時に確認する。会話ペインは`try/finally`相当の構造でこれを保証する。

分類は**受信完了時に1度だけ**（emotion-classification.md）。streaming中に逐次分類すると「エラーが出ましたが」の時点で`worried`が出て直後に`proud`へ飛ぶ百面相になる。

### 論点4: エラーの見せ方

chat-adapter-errors.md の決定をUIに落とす。**アプリが自分の状態について嘘をつかない**（constraints.md）。

| 状況 | 会話ペインの表示 | 灯里 |
|---|---|---|
| リトライ中（SDK内部） | **何も出さない**。`thinking`のまま | `thinking`（`worried`を出さない） |
| リトライを尽くして失敗（429/5xx/通信断） | エラー吹き出し + 「モックモードに切り替える」ボタン | `panic` |
| 401/400/404（リトライ不能） | エラー吹き出し + 「モード設定を開く」ボタン | `worried` |
| 無通信タイムアウト | エラー吹き出し + 再送ボタン | `panic` |

**リトライ中に何も出さない**のは、429のリトライが実測2.0秒で完結する一方 `reactionDurationMs` が3000msであり、`worried`を出すと**成功した後もまだ心配顔が残る**ため（chat-adapter-errors.md）。UI側でも同じ理屈で、一瞬のリトライにスピナー以上のものを出さない。

**mockへの自動フォールバックはしない。** ボタンを添えてユーザーが押した時だけ切り替える。mockは固定返答なので、黙って落とすと「ユーザーの質問に対してあらかじめ用意された固定文がClaudeの回答であるかのように返る」ことになる（chat-adapter-errors.md）。

エラー文言は`net.isOnline()`で出し分ける（制御フローは変えず、文言だけ）。

### 論点5: `activeAdapter` との関係（決定: 案1）

**FR-1は「Code Adapter / Chat Adapterを手動で切替える」と定め、5.3は「どちらも同一のEmotionEngineインスタンスを共有」としている。** すると次の状態が起こりうる。

- `activeAdapter === 'code'` のまま、ユーザーが会話ペインでメッセージを送る
- Claude Codeの実況（`PreToolUse` → `thinking` 等）と、Chatの応答（`classify` → `happy` 等）が**同一のEmotionEngineに同時に流れ込む**
- 灯里の表情がCode由来かChat由来か区別できなくなる

これは会話ペインを常時表示（既定で展開）にしたことで顕在化した。**独立ウィンドウで「開いている間だけChat」なら曖昧さは小さかったが、常に見えているUIから常に送信できる**以上、決着が要る。

考えられる案:

1. **送信時に`activeAdapter`を`'chat'`へ自動切替し、その旨を会話ペインに明示する**（「Chatモードに切り替えました」）。黙って切り替えない。ただしFR-1の「手動で切替」の変更にあたる可能性がある。
2. **`activeAdapter !== 'chat'` の間は送信をブロックし、「Chatモードに切り替えてください」と表示する**。FR-1を変えずに済むが、常時見えている入力欄が押せないのは体験として鈍い。
3. **会話ペインの展開/折りたたみを`activeAdapter`に連動させる**（Chatモード時だけ展開可能）。C-21の「既定で両方展開」と衝突する。

> **決定（2026-07-18）**: **案1を採用**（C-24）。会話ペインからの送信時に`activeAdapter`をChatへ自動切替し、「Chatに切り替えました」と会話ペインに明示する（黙って切り替えない）。FR-1「手動切替」の唯一の例外として要件定義書4.1・基本設計書5.3に反映済み。ユーザーが会話ペインに打ち込む行為自体が「今はChatをしたい」という意思表示であり、それに合わせて状態を変え、変えたことを隠さないのが自然なため。

### 論点6: キャラクターウィンドウとの関係

FR-9（表示排他制御）の削除により、**会話ペインとキャラクターウィンドウは排他ではない**。同時に見えていてよい。

キャラクターウィンドウは既定で`clickThrough: true`・透過・最前面であり、会話ペインの上に浮いている可能性がある。ただし character-window.md の初期配置は**プライマリのworkArea右下**で、Control Panelウィンドウは中央付近に出るため、既定では重ならない。重なった場合もクリックスルーが既定なので操作を妨げない。

**会話ペインは灯里の描画を持たない。** 憑坐状態帯（呪紋リング+Mood）だけを持ち、キャラクター本体は`CharacterRenderer`を通じてキャラクターウィンドウに描かれる。model-mapping-ui.md がマッピング編集用のプレビューでControl Panel側に`CharacterRenderer`を持ち込んでいるが、あれはマッピング検証のための一時的なマウントであり、会話ペインには要らない（会話中の灯里はキャラクターウィンドウで見る）。

### 論点7: 入力欄まわりの機能（C-23）

会話ペインの入力欄に、Claude / Claude Code に相当する操作機能を持たせる（2026-07-18 デザイン承認済み。視覚リファレンスはモックのArtifactで確認した）。

| 機能 | 挙動 | 備考 |
|---|---|---|
| スラッシュコマンド | `/clear`(会話クリア=メモリ破棄)・`/mock`・`/real`・`/code`・`/panel`・`/model` | モード/アダプタ切替・設定を開くUIショートカット。agenticではない |
| @参照 | 作業ログ(直近hooks)・表示中のモデル・設定を、ユーザーが明示選択して文脈に含める | **ツール呼び出しではなくユーザー選択の限定的文脈参照**（要件10章のagenticとは別）。参照対象はアプリ管理の固定対象に限り、本文文字列から任意パスを解決しない（security.md） |
| 添付 | 画像・ファイルの添付 | **real時のみ**。mock時は無効。ダイアログで選んだファイルに限定（security.md） |
| 応答モデル選択 | Opus 4.8 / Sonnet 5 / Haiku 4.5 | **real時のみ**有効。`config.chatAdapter.model`に保存。mockは固定返答のため無効（C-08維持） |
| 停止 | 応答中の中断 | 中断時も**必ず`release('thinking')`を呼ぶ**（成功・失敗・中断・無通信の全経路。論点3） |
| メッセージ操作 | 応答へのコピー・再生成 | — |
| コンテキスト使用量表示 | real時は実測値 | **mock時は実測値を持たないため誇張して見せない**（constraints.md「嘘をつかない」） |
| 入力ヒント | Enter送信 / Shift+Enter改行 / `/`コマンド / `@`参照 | — |

**real専用機能の切り分け**: 添付・応答モデル選択・コンテキスト実測はいずれもrealでのみ意味を持つ。mock既定（C-08）は崩さず、mock時はこれらのコントロールを無効表示にする。

**将来検討（v1では入れない）**: Code Adapterの作業状況をChatへ**自動**で取り込む機能（自動参照）。@参照はユーザーが明示的に選ぶのに対し、自動参照はagentic寄りになるため要件10章のスコープ外に留める（採用しなかった第3の候補）。

### 形式による分岐について

**会話ペインはLive2D/スプライトセットのどちらにも依存しない。** キャラクターの描画を持たず、EmotionEngineへ`trigger`/`release`を送るだけで、`CharacterRenderer`に触れない。EmotionEngineが形式を意識しない設計（basic-design.md 5.1）がそのまま効いている。憑坐状態帯が表示するのはMood（`THEMES.moods`の色・ラベル・回転速度）であり、これはモデル形式と無関係。
