# lipsync.md — リップシンクとstreaming表示の同期方式

**ステータス**: 確定(2026-07-16)
**対応FR**: FR-3(Chat Adapter)、FR-4(EmotionEngine)
**関連**: emotion-classification.md、data.md 2.2章、要件定義書 C-12・C-16・C-18

## 背景

Chat Adapterのstreaming応答表示と、キャラクターの口パクアニメーションをどう同期させるかが未確定。v1のスコープはテキスト+アニメーションのみで、音声(TTS)は将来検討のため、**音声波形に基づくリップシンクではなく、テキスト表示速度に基づく口パク**になる想定。

## 結論

| 論点 | 決定 |
|---|---|
| リップシンク | **v1では実装しない** |
| `talking`状態の新設 | **しない**(11状態化はFR-4の変更を招き、かつ目的を達成しない) |
| streaming中のキャラクター | **`thinking`を応答完了まで持続させる**(両形式で同一) |
| `loop`と状態の寿命 | **直交する別概念として分離する**(data.mdの「要再検証」への回答) |
| mock/real | 同一経路。**mockの固定返答も擬似streamingで流す** |

## 検討ログ

### 論点3から先に答える: スプライトセットはリップシンクが原理的に不可能

本ドキュメントの論点は「同期方式」を問うているが、掘ると**v1でリップシンクは成立しない**。理由は論点3にある。

スプライトセットのクリップは**事前レンダリング済みのアニメーションWebP**である。口の動きはピクセルに焼き込まれており、`SpriteSetRenderer`はWebPを再生するだけで、口だけを独立に動かす手段を持たない。元が静止画1枚+外部AI生成動画である以上、口のレイヤーが分離されていない。合成し直す余地がない。

一方Live2Dは`ParamMouthOpenY`のようなパラメータで口を駆動できる。

これは`CharacterRenderer`の抽象化では吸収できない**根本的な非対称**である。インターフェースは`setState(stateKey)`しか持たず、口の開閉度を渡す口がそもそもない。仮に`setMouthOpen(v)`を足しても、`SpriteSetRenderer`側は**何もできないので空実装になる**。

> **一部確認済み(A2) / 駆動自体はv1で不要**: `pixi-live2d-display`は導入済み、開発用モデルも`dev-assets/live2d/`に配置済みになった。開発用モデルの定義ファイルを実測したところ:
> - Cubism4(Haru)は`model3.json`の`Groups`で`{"Name":"LipSync","Target":"Parameter","Ids":["ParamMouthOpenY"]}`を**自己宣言**しており、口駆動パラメータが`ParamMouthOpenY`であることは確認できた。
> - Cubism2(Shizuku)には`Groups`宣言が**無い**(lipSync対象パラメータの宣言方式がCubism4と異なる。Cubism2は`.model.json`側にlipSync宣言を持たず、パラメータIDを別途決め打つ必要がある)。**これも形式間の非対称の一つ**。
>
> ただし`ParamMouthOpenY`を実際に**駆動して口が動くか**はWebGL描画を要するためGUI無しでは実測できていない。もっとも、後述のとおりv1ではリップシンクを実装しないため、この駆動確認は不要のまま据え置く。

#### Live2Dだけ実装する案を退ける

技術的にはLive2D側だけリップシンクを実装できる。しかし**採らない**。

要件定義書C-16は**スプライトセット=標準の入口(おすすめ)、Live2D=上級者向け**と定めている。Live2D限定でリップシンクを付けると、**おすすめしている形式のほうが体験が劣る**という反転が起きる。「画像1枚から始められる敷居の低さ」が売りの形式が、機能の劣る廉価版として位置づけられてしまう。それは形式の位置づけを設計者の意図と逆向きに壊す。

#### `talking`状態の新設を退ける

論点3は「専用の`talking`状態を新設するか、既存の10状態に含めるか」と問い、自ら「FR-4の変更を伴う可能性がある」と注記している。**新設しない。**

- **10状態は3箇所で「単一の情報源」と宣言されている**(要件定義書4.4、`src/shared/emotions.ts`、モックアップのコメント)。11状態化はFR-4の変更、すなわちNotion正本の変更を伴う。
- C-18により、マッピング編集画面には**常に全状態が提示される**。11個目が全ユーザーに見える。
- スプライトセット形式では`talking.webp`を追加生成する必要がある。つまり**ユーザーが外部AIで動画をもう1本作る**。敷居の低さが売りの形式に、もう1本分の負担を課すことになる。
- **そして決定的なことに、その`talking.webp`を再生しても口パクにはならない**。事前レンダリングされた動画なので、テキストの表示速度と同期しようがない。**負担だけが増えて目的を達成しない。**

### v1でリップシンクをやらない決定的な理由: 音声がない

要件定義書C-12は**TTSをv1スコープ外**と定めている。

音声が無い以上、テキストの表示速度に合わせて口を動かしても、**テキストが既に伝えている情報を装飾するだけ**である。リップシンクの本来の価値は「聞こえている音と口の形が一致していること」にあり、音が無ければその価値は生じない。無音のまま口だけがパクパクする表現は、コストに見合わない。

将来TTSを導入したとき(C-12「将来検討」)に初めてリップシンクは意味を持つ。**そのときにスプライトセットの原理的不可能性が本当の問題として立ち上がる**ため、TTS検討時にはこの非対称の解消(レイヤー分離した素材形式の導入等)を併せて設計する必要がある。本ドキュメントはその論点を将来へ引き継ぐ。

### 本当の論点: streaming中にキャラクターは何をするのか

リップシンクを外すと、残る実質的な問いはこれである。答えは既に他の設計が出している。

emotion-classification.mdの決定により、**メッセージ送信時に`thinking`が発火する**(テキスト分類ではなくイベント駆動)。両形式とも自分の`thinking`クリップ/モーションを再生するだけなので、**形式に依存しない**。`CharacterRenderer.setState('thinking')`を呼ぶだけで済む。

#### 発見した問題: `thinking`が応答より先に終わる

しかし現状の設定のままでは破綻する。

- `clips.thinking`は`loop: false` + `returnTo: 'idle'`(data.md 2.2)
- `emotionEngine.reactionDurationMs`の既定は**3000ms**

つまり20秒かかる応答では、**3秒で`thinking`が終わり、残り17秒は`idle`に戻る**。Claudeがまだ生成中で、テキストが画面に流れ続けているのに、灯里は待機顔で突っ立っている。streaming表示との同期という本ドキュメントの主題からすると、これが一番大きな不整合である。

原因は、**同じ`thinking`状態がAdapterによって寿命が違う**ことにある。

| Adapter | `thinking`の起点 | あるべき寿命 |
|---|---|---|
| Code Adapter | `PreToolUse` | **一過性**。ツール実行は短く、3秒で戻ってよい |
| Chat Adapter | メッセージ送信 | **持続**。応答が完了するまで続くべき |

#### `loop`と状態の寿命は直交する

data.md 2.2は末尾でこう述べている。

> Mood(idle/confident/tired)は`loop: true`、Reaction(thinking/happy/proud/worried/curious)は`loop: false`+`returnTo: "idle"`が基本パターン。panic/sleepyはReactionだが継続性のある状態なのでループ扱いとする(**実装時に要再検証、詳細設計で確定**)。

この「要再検証」に答える。**`loop`と状態の寿命は別の概念であり、data.mdはこの2つを混同している。**

- **`loop`(manifest.jsonの責務)**: 素材の再生方法。クリップが状態の継続時間より短いとき、つなぎ直すか、最終フレームで止めるか。
- **状態の寿命(EmotionEngineの責務)**: いつMoodへ戻るか。タイマーで戻るか、条件が解除されるまで持続するか。

この2軸で10状態を整理すると、data.mdの注記が引っかかっていた点も解ける。

| 状態 | `loop` | 寿命 | 理由 |
|---|---|---|---|
| idle / confident / tired | true | Mood(そもそも戻り先) | — |
| happy / proud / worried / curious | false | タイマー(3秒) | イベントへの一過性の反応 |
| **panic** | **true** | **タイマー(3秒)** | クリップが3秒より短ければループさせたい。だが状態自体は一過性でよい(エラーは既に起きた出来事) |
| **sleepy** | **true** | **持続** | 無操作5分という**条件が続く限り**眠い。3秒で目覚める理由がない。操作があった時点で解除される |
| **thinking** | **true**(変更) | **Code=タイマー / Chat=持続** | 同上。応答を待っている間ずっと考えている |

**`panic`と`sleepy`はどちらも`loop: true`だが、寿命は正反対**である。data.mdが両者を「継続性のある状態」と一括りにしていたのは、`loop`と寿命を同一視していたためで、この2つを分ければ矛盾なく説明できる。

#### 決定: `thinking`を持続させる

```typescript
// Chat Adapter: 送信時
engine.trigger('thinking', { sustain: true });
// 応答完了時(成功・失敗いずれも)
engine.release('thinking');

// Code Adapter: PreToolUse — 従来どおり一過性
engine.trigger('thinking');
```

`sustain: true`が付いたReactionは`reactionDurationMs`のタイマーを起動せず、明示的な`release()`までMoodへ戻らない。`sleepy`も同じ仕組みで、無操作タイマーで`sustain`付き発火し、操作を検知したら`release`する。

**`release()`の呼び忘れは`thinking`の永久固着を招く**。chat-adapter-errors.mdが確定させた無通信ウォッチドッグは、この観点でも必須である(SDKの`timeout`が凍ったstreamに効かないため、それが無いと応答が凍ったまま`release`が永久に呼ばれない)。成功・失敗・中断のすべての経路で`release`が呼ばれることを、実装時に必ず確認する。

> **要決着**: `sustain`/`release`はEmotionEngineのAPI変更であり、basic-design.md 5.2 = **Notion正本の変更**を伴う。5.2は現在「Reactionはタイマー(3秒目安)でMoodに自動復帰」としか書いていない。本ドキュメントでは決定しない。

`clips.thinking`の`loop`を`false`→`true`へ変更する点は、data.md 2.2が明示的に詳細設計へ委ねている事項なので本ドキュメントの決定に含め、data.md側も併せて更新する。

#### 対称性チェックで見つかった穴: Live2D側に`loop`の対応物がない

`loop`はスプライトセット形式の`clips`にしか存在しない。Live2D形式の`emotionMap`は`{ motion, expression }`のみで、**ループの概念を持たない**(data.md 2.1)。

ここで問題になる。`thinking`を20秒持続させたとき、**Live2Dのモーションが尽きたら何が起きるのか**。Cubismのモーションは通常数秒で終わる。最終フレームで固まるのか、自動でループするのか、ニュートラルへフェードするのかは、Cubism側のモーション定義(`model3.json`)と`pixi-live2d-display`の再生実装に依存する。

つまり**スプライトセット側だけ`loop: true`にして満足すると、Live2D側では持続中に灯里が固まる**可能性がある。これはCLAUDE.mdが警告する「片方だけ直して満足する」失敗そのものである。

> **コード実測で判明(A2) / 実描画での最終確認は実装時**: `pixi-live2d-display`(v0.4.0)のバンドルソースを読解し、開発用モデル(`dev-assets/live2d/`)の定義ファイルと突き合わせて、以下を確定した。**WebGL描画を伴う最終確認は実装時に行う**が、挙動はライブラリ実装から一意に決まる。
>
> **① 尽きたときの挙動 = idleグループへ自動フォールバック(固まらない)。**
> 基底`MotionManager.update()`(Cubism2/4共通)は、再生中モーションが`isFinished()`になり他に予約が無いとき(`shouldRequestIdleMotion()`)、`startRandomMotion(this.groups.idle, MotionPriority.IDLE)`で**idleグループのモーションを自動再生する**。`groups.idle`はCubism4が`"Idle"`、Cubism2が`"idle"`(いずれもManagerがハードコード)。dev-assetsの両モデルとも該当グループを持つ(Haru: `"Idle"` 3件 / Shizuku: `"idle"` 3件)。
> → **最終フレームで固まることはない。idleへフェードして戻る。**
> → ただし**idleグループを持たないモデルはフォールバック先が無く固まりうる**。モデル取り込み時にidleグループの存在を検証すべき(model-mapping-ui.mdの自動検出に条件を足す)。
>
> **② 個々のモーションはループしない(Cubism4で確認)。** **Cubism4**の`createMotion`はfade時間のみ設定し`setIsLoop`を呼ばないため、`model3.json`のmotionが`Meta.Loop:true`(Haru idleは実際にtrue)でも`_isLoop`は既定`false`のまま。idleが継続して見えるのは、終了ごとにidleグループから**別モーションを再抽選**するため。
> なお**Cubism2**の`createMotion`(`index.es.js` L1638-1644)は`setFadeIn`/`setFadeOut`のみで、モーション実体`Live2DMotion`は外部ランタイム`live2d.min.js`のクラス(`node_modules`に実体が無い)であるため、`setIsLoop`相当の有無はコードから直接確認できていない。ただし①のidleフォールバックはCubism2/4共通の基底`MotionManager.update()`で確認済みのため、仮にCubism2側に何らかのループ挙動があっても③の結論は揺らがない。
>
> **③ 帰結: 非idleのReaction(thinking等)の持続はモデル任せにできない。** モーションが尽きると①でidleへ戻ってしまうため、寿命ぶん同じ表出を続けたいなら**EmotionEngine側で寿命の間モーションを再発火する**必要がある。②のとおりライブラリのstartMotionはループ属性を持たないので、`emotionMap`に`loop`相当を足しても効かない。
> → したがって当初想定した「**data.md 2.1(Live2Dのmanifest)に`loop`を足す**」対応は**不要**。持続の管理はEmotionEngineの責務に寄せる(スプライトセットの`loop`はあくまで素材の再生方法であり、Live2Dに対応物を持たせない = この非対称は正当)。

### 論点1・論点2について

**論点1(同期の粒度: 1文字ごとか、単語単位か、一定間隔か)** および **論点2(`ParamMouthOpenY`の更新頻度)** は、リップシンクを実装しない決定により**v1では検討不要**となる。

将来TTS導入時に再検討する際の材料だけ残しておく。

- 非機能要件は「無操作時にfpsを落とす(60→15fps目安)」と定めている。口パクを毎フレーム更新する実装は、このfps制御と衝突しうる(喋っている間は無操作でも60fpsを維持する必要がある)。
- そのときスプライトセット側は前述のとおり原理的に追随できないため、**素材形式そのものの見直し**(口のレイヤー分離)が前提になる。

### 論点4: mock/real両方での動作

**両方で同一に動作する。加えて、mockの固定返答も擬似的にstreamingで流す。**

論点は「mockモードでも同様の口パク表現を行うか(答えは恐らくYES、モック段階でも動作確認したいため)」だが、リップシンクを実装しないので、正確には「mockでも`thinking`の持続を行うか」という問いになる。答えはYES。

ただし**mockの返答が即座に返るなら`thinking`は一瞬で終わり、持続の経路が一度も実行されない**。emotion-classification.mdが「既定モードがmockである以上、日常の開発でこの経路が動き続け、実装が腐らない」という理由でmockにも分類器を通すと決めたのと同じ理屈で、**mockも固定返答を1文字ずつ(あるいは数文字ずつ)遅延を挟んで流す**。

これにより、既定のmockモードのまま以下がすべて日常的に検証される。

- `thinking`の`sustain` → `release`の往復
- streaming表示のUI
- 分類器の実行(emotion-classification.md)

realに切り替えて初めて経路が動く、という状態を作らない。C-08により既定はmockであり、**開発中に最も動く経路がmockだからこそ、そこを本番と同じ形にしておく**。
