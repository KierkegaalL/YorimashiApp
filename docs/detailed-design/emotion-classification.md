# emotion-classification.md — キーワードベース感情分類の具体的な辞書/ロジック

**ステータス**: 確定(2026-07-16)
**対応FR**: FR-3, FR-4
**関連**: basic-design.md 5.2(EmotionEngine)、chat-adapter-errors.md、要件定義書 C-08

## 背景

Chat Adapterのmockモードおよびrealモードの初期実装は、Anthropicの応答テキストをキーワードベースで感情(EmotionEngineの10状態のいずれか)に分類する想定。具体的な辞書・ロジックは未確定。

## 結論

| 論点 | 決定 |
|---|---|
| 辞書の対象 | **10状態ではなく5状態**(panic / proud / worried / happy / curious)のみ |
| スコアリング | 重み付きキーワードの**合計**。同語の連発は2回で頭打ち |
| 否定表現 | キーワード直後10文字を走査して打ち消す。定型句は除外指定 |
| 優先順位 | **スコアが先、同点時のみEmotionEngineの優先度**で決着 |
| 分類の実行点 | 応答の**受信完了時**に1度 |
| Haiku分類 | mockでは**絶対に使わない**。realでも既定オフのフラグ制 |

## 検討ログ

以下のロジックは実際にコードとして書き、日本語のアシスタント応答を模したテキスト11件で実行して検証した。

### 論点1: 10状態それぞれに対応するキーワード辞書

#### 辞書が必要なのは5状態だけ

本ドキュメントは当初「対象の10状態それぞれに対応するキーワード辞書」を論点としていたが、**10状態のうち5つはそもそもテキストから分類されない**。EmotionEngineの設計(basic-design.md 5.2)を辿ると発火源が別にあるためである。

| 状態 | 発火源 | 辞書 |
|---|---|---|
| idle / confident / tired | **Mood層**。`successStreak`/`failStreak`による遷移 | 不要 |
| thinking | メッセージ**送信イベント**(応答待ちの状態そのもの) | 不要 |
| sleepy | **タイマー**。`emotionEngine.idleTimeoutMs`(既定5分)の無操作 | 不要 |
| panic / proud / worried / happy / curious | 応答テキストの分類 | **必要** |

Mood 3種にキーワード辞書を用意しないのは重要な点である。5.2は「successStreak/failStreakによりMood自体も遷移」と定めており、Moodはテキストの内容ではなく**成否の積み重ね**から決まる。応答に「疲れました」とあっても`tired`にはしない。テキストからMoodを触れるようにすると、Mood層とReaction層を分けた2層構造そのものが崩れる。

`sleepy`と`thinking`も同様に、テキストの意味ではなく**時間と状態**に属する。「眠い」と書かれた応答で`sleepy`を出す実装は、無操作5分という本来の意味を壊す。

なお`panic`はテキストからも分類するが、**主たる発火源はAPIエラー**(レート制限・ネットワーク断)であり、その扱いはchat-adapter-errors.mdで確定させる。本ドキュメントの辞書は、応答本文が明確な異常を報告している場合を拾う補助的な位置づけ。

#### 辞書

```typescript
type ChatReaction = 'panic' | 'proud' | 'worried' | 'happy' | 'curious';

/** [語, 重み, 否定スキャン除外?] */
const KEYWORDS: Record<ChatReaction, [string, number, boolean?][]> = {
  panic:   [['致命的', 3], ['クラッシュ', 3], ['緊急', 3], ['データが失われ', 3],
            ['危険', 2], ['重大', 2]],
  proud:   [['完了しました', 3], ['解決しました', 3], ['完璧', 3], ['全て通り', 3],
            ['すべて通り', 3], ['成功', 2], ['通りました', 2]],
  worried: [['申し訳', 3, true], ['すみません', 3, true], ['エラー', 2], ['失敗', 2],
            ['警告', 2], ['問題', 1], ['注意', 1]],
  happy:   [['できました', 2], ['いいですね', 2], ['ありがとう', 2], ['素晴らし', 2],
            ['助かり', 2]],
  curious: [['でしょうか', 1], ['どちら', 1], ['確認させて', 2], ['教えてください', 2]],
};
```

重みは「その語がどれだけ単独で状態を決定づけるか」で置いている。`問題`(1)は「問題ありません」「問題の切り分け」など中立文脈にも現れるため低く、`致命的`(3)はほぼ異常時にしか出ないため高い。

**`！`や`？`のような記号は辞書に入れない**。当初`happy`に`！`、`curious`に`？`を含めて試したが、技術的な応答では強調や反語で頻出し、ノイズにしかならなかった。

#### 否定表現の打ち消し

素朴なキーワード一致は日本語の否定で破綻する。実測で「エラーは出ませんでした。」が`worried`に分類されることを確認した。

対策として、キーワードに一致した直後10文字を走査し、否定表現があればその一致を無効にする。

```typescript
const NEG = /(ませんでし|ません|なかった|ないです|ない|無い|ず(に|、|。))/;
const WINDOW = 10;
```

**ここに罠がある**。`申し訳ありません`・`すみません`は、語そのものが「ません」を含む定型句である。否定スキャンを一律に適用すると、**最も明確な`worried`のシグナルが自分自身の「ません」で打ち消される**。よって辞書の第3要素で否定スキャンの除外を指定する(上表の`true`)。これは実測で発覚した挙動であり、指定を外すと「申し訳ありません、失敗しました。」が無反応になる。

#### 検証結果

| 入力 | 判定 | 期待 | |
|---|---|---|---|
| エラーが出ていますね。修正してみます。 | worried | worried | OK |
| エラーは出ませんでした。 | 無反応 | 無反応 | OK |
| 申し訳ありません、失敗しました。 | worried | worried | OK |
| 問題ありません。 | 無反応 | 無反応 | OK |
| 失敗しませんでした。 | 無反応 | 無反応 | OK |
| テストが全て通りました！完了しました。 | proud | proud | OK |
| 致命的なエラーです。データが失われた可能性があります。 | panic | panic | OK |
| エラーは出ましたが、修正できました。完了しました。 | proud | proud | OK |
| できました! | happy | happy | OK |
| どちらの方法にしますか?教えてください。 | curious | curious | OK |
| エラーは、今回のケースに限っては出ませんでした。 | **worried** | 無反応 | **NG** |

10/11。「問題ありません」「失敗しませんでした」が正しく無反応になっている点は、否定スキャンが効いている証拠。

**唯一の失敗は否定がスキャン窓(10文字)の外にある場合**。「エラーは、今回のケースに限っては出ませんでした。」は`エラー`と`ません`が離れすぎている。窓を広げると今度は無関係な否定を拾うため、根本的にはキーワード方式の限界であり、論点3(Haiku分類)の移行理由そのものになる。**この限界を承知の上でv1はキーワード方式で始める**(誤って`worried`が出ても3秒でMoodへ復帰するだけで、実害が小さいため)。

### 論点2: 複数キーワードが同時にマッチした場合の優先順位

**スコアで決め、同点のときだけEmotionEngineの優先度(panic > proud > worried > happy > curious)を使う。**

当初の論点は「EmotionEngineの優先度をそのまま流用するか、独自の優先度を持つか」だったが、**どちらでもない**。優先度を第一の判断基準にすると誤分類する。

決定的な例が「エラーは出ましたが、修正できました。完了しました。」である。この文は`worried`(エラー:2)・`happy`(できました:2)・`proud`(完了しました:3)の3つに一致する。

- **優先度をそのまま流用した場合**: panic > **proud** … の順なので proud。ここは偶然正しいが、たとえば「エラーが出ましたが、大丈夫です」のように proud 語が無い場合、worried > happy の順で `worried` が勝つ。文全体の結論は肯定なのに心配顔になる。
- **スコアで決めた場合**: proud(3) > worried(2) = happy(2) となり `proud`。実測で確認済み。

EmotionEngineの優先度は本来、**時間軸上で競合する複数のReactionを調停する**ためのもの(再生中のpanicがhappyに割り込まれないようにする等)であって、**1つのテキストが何を意味するかを決める道具ではない**。役割が違うものを流用すると、上記のように結論を取り違える。

一方で、同点時の決着には優先度をそのまま使う。ここで独自の順序を作ると情報源が二重化するため、新しい概念を持ち込まない。

合計スコア方式には「長文ほどスコアが伸びる」性質があるが、**状態間の相対比較しかしない**(閾値を持たない)ため問題にならない。同語の連発だけは2回で頭打ちにし、同じ単語の繰り返しでスコアが暴走しないようにする。

### 論点3: Haiku分類への移行基準

#### mockでは絶対に使わない

要件定義書C-08は「Chat Adapterの既定モードは**mock**、課金トリガーはreal切替時のみ」と定める。**mockモードでHaiku分類を呼ぶと、この確定事項が壊れる**(mockのままAPI課金が発生する)。したがってmockは常にキーワード分類のみ。論点として挙がっていた「mock時はHaiku分類も使わない、が自然だが要確認」への答えは**そのとおり**で、これは自然というより要件上の必須条件である。

なおmockの返答は固定であるため、キーワード分類の結果も固定になる。それでも**mockでキーワード分類を実際に走らせる**ことに意味がある。既定モードがmockである以上、日常の開発でこの経路が動き続け、分類ロジックの実装が腐らない。mockのエントリに感情を直接持たせる(分類を迂回する)設計にはしない。

#### realでも既定はキーワード。Haikuはフラグでオプトイン

「キーワードの精度が不十分になったら切り替える」という自動フォールバックにはしない。分類の良し悪しは自動判定できず、**判定できない基準で自動的に課金が始まる**のは避けたい(1メッセージごとに追加のAPI呼び出しが発生する)。

よって明示的なフラグで切り替える。移行を検討する判断材料は上記の検証で具体的に見えている。

- 否定がスキャン窓の外にある文(実測で確認した唯一の失敗ケース)
- 皮肉・反語・婉曲表現
- 文脈依存(直前のやり取りを踏まえないと意味が決まらない応答)

これらが実使用で目立つようになったら切り替える、という運用判断とする。

Haiku分類には**応答完了後に追加の往復が入る**ため、リアクションの発火が1秒前後遅れる点にも注意する。キャラクターの反応が遅れるのは体験上のコストであり、精度と引き換えになる。

> **要決着(config schemaの変更が必要)**: 現在の`chatAdapter`は`{ mode, anthropicApiKey, model }`しか持たず、**分類器を選ぶフィールドが無い**。`classifier: z.enum(['keyword','haiku']).default('keyword')`と、分類用モデルID(本文用の`model`とは別)の追加が要る。basic-design.md 6.1 = Notion正本の変更を伴うため、本ドキュメントでは決定しない。

#### 参考: 将来の第3の選択肢

本文生成のシステムプロンプトでClaude自身に感情タグを出させれば、**追加コストも追加レイテンシもゼロ**で分類できる。ただし応答本文にタグが混ざるため除去処理が要り、ユーザーが見るテキストに手を入れることになる。今回は採らないが、Haikuより筋が良い可能性があるため記録しておく。

### 分類の実行点

**応答の受信完了時に1度だけ分類する。** streaming中に逐次分類すると、文の途中(「エラーが出ましたが」まで)で`worried`が出て、直後に`proud`へ飛ぶ、という顔の百面相が起きる。上記の「結論は文末にある」という性質と真っ向から衝突する。

- 送信時 → `engine.trigger('thinking')`(テキスト分類ではなくイベント)
- 受信完了時 → `classify(text)` → 一致すれば`engine.trigger(state)`、スコア0なら**何もしない**(Moodのまま)

スコア0で無理に`idle`等を発火させない。該当なしは「反応する理由が無かった」であって、それ自体が正しい状態である。

クールダウン(既定1.5秒)による連発抑制はEmotionEngine側の責務であり、分類器は`trigger()`を呼ぶだけで関知しない。

### 分類対象のテキスト

**Claudeの応答テキストのみを対象とする。ユーザーの入力は分類しない。**

本ドキュメントの背景が「Anthropicの応答テキストを分類する」と定めているため、その範囲に留める。ユーザーが「ありがとう!」と書いたときに灯里が喜ぶ挙動は自然に思えるが、それは**要件に無い挙動の追加**であり、勝手に入れない。入れる場合はFR-3の変更としてNotion側から始める。
