# ヨリマシ.app — 開発ポートフォリオ

> macOS向けデスクトップ常駐アプリ。Claude Codeでの作業実況とClaudeとのチャット対話に、憑坐(よりまし)キャラクター「常世灯里」が感情豊かに反応しながら伴走する。開発者自身のClaude Code活用基盤(ハーネスエンジニアリング)の一環として、Claude Codeと協働しながら設計・実装した。

## 概要

- **開発期間**: 2026-07-16 〜 2026-07-30(約2週間)
- **コミット数**: 102件 / **マージ済みPR**: 24件
- **コード規模**: TypeScript約19,500行(Main/Preload/Renderer/共有スキーマ)
- **詳細設計ドキュメント**: 8件、すべて「実測に基づく決定」で確定
- **開発体制**: 1名(プロダクトオーナー兼レビュアー) + Claude Code(実装エージェント)

## 何を作ったか

- **Code Adapter**: Claude Codeのhooksイベント(`PreToolUse`/`PostToolUse`等)をローカルサーバーで受け取り、ツールの実行・失敗・待機状況に応じてキャラクターが反応する
- **Chat Adapter**: コントロールパネル内の会話ペインからClaude(Anthropic API)と直接チャットできる。無課金で挙動確認できる`mock`モードと実接続する`real`モードを切り替え可能
- **EmotionEngine**: 気分(idle/confident/tired)+反応(thinking/happy/proud/worried/panic/curious/sleepy)の計10状態を、優先度・クールダウン・連続成功/失敗による遷移で管理
- **2形式のキャラクター描画**: Live2D(Cubism 2/4/5、上級者向け)とスプライトセット(画像1枚からAI生成アシストで作成、標準の入口)を`CharacterRenderer`インターフェースで抽象化
- **セキュリティ設計**: ローカルサーバーは127.0.0.1限定バインド、全リクエストにトークン認証、パストラバーサル・zip-slip・シンボリックリンク対策

## 技術スタック

| 領域 | 採用技術 | 採用理由 |
|---|---|---|
| デスクトップ基盤 | Electron + TypeScript + React + Vite(electron-vite) | 透過ウィンドウ・常時最前面・クリックスルーというFR-6の要件をNext.js/Rails単体では満たせないため、Electron一択で確定 |
| Live2D描画 | PixiJS **v6系固定** + pixi-live2d-display | `pixi-live2d-display`安定版が`pixi.js: ^6`をpeerDependencyに要求。v8(npm最新)へ安易に追従すると`Live2DModel`が別クラス扱いになり描画が壊れることを実測で確認し、意図的にv6へ固定 |
| 設定管理 | Zod(`schemaVersion`によるマイグレーション対応) | config.jsonの後方互換性を型レベルで担保 |
| ローカルサーバー | Node.js(`http`+`ws`)、127.0.0.1限定バインド | hooksイベント受信とWS配信を1プロセスで完結させつつ外部露出を最小化 |
| Chat Adapter | `@anthropic-ai/sdk`(公式SDK) | 独自にリトライ・タイムアウトを実装せず、SDKの`maxRetries`/`AbortSignal`に委ねる設計判断(後述) |

## アーキテクチャ上の工夫

- **Adapterパターン**: Code Adapter / Chat Adapterが同一のEmotionEngineを共有し、入力元が増えても感情表現ロジックを重複させない
- **全10状態の単一の情報源**: `src/shared/emotions.ts`一箇所が状態定義の正であり、Live2Dのモーション対応・スプライトセットのクリップ対応・感情分類器のいずれもここを参照する
- **対称性設計の徹底**: `CharacterRenderer`インターフェースでLive2D/スプライトセットの実装を抽象化。この抽象化の裏で「片方の形式だけ直して他方を直し忘れる」事故が開発中に2度発生したため、PostToolUseフックで差分を機械的に検知する仕組みを自作し(後述)、以降の再発を防止した
- **「アプリが自分の状態について嘘をつかない」設計原則**: real接続失敗時にmockへ自動フォールバックしない、設定不備は「未設定」とそのまま表示する等、失敗を隠蔽しない方針を一貫させた

## 技術的に難しかった点

### 1. Live2D描画バグの多段階調査 — ヒューリスティックの限界を実測で突き止める

Live2Dモデルの一部パーツ(瞳・口)が別のパーツに覆われて表示されない不具合が発生。調査は以下の順で進んだ。

1. Cubism CoreのAPIが`drawables.renderOrders`から`drawOrders`へ内部的にリネームされていたことを、ライブラリソースを直接読んで発見
2. `drawOrders`はCubism Editor向けの粗いZ値でしかなく、そのまま使うと1パーツしか描画されないと判明。密な順列への変換ロジックを実装
3. 同値タイの並び順を`parentPartIndices`昇順で解決する応急処置を実装し、いったん瞳の重なり順バグを解消
4. ユーザーが別モデルに差し替えたところ、今度は口がリボンに隠れる新たな不具合が発生。三角形レベルのラスタライズ検証(頂点座標をグリッドに離散化し実際に点内判定)まで踏み込んで調べた結果、**手順3の「Part index昇順」ルールは瞳のケースと口のケースで正反対の答えを要求する、数学的に矛盾したヒューリスティックだった**ことを証明
5. Cubism Coreの生のミニファイ済みJSソースを`grep`で読み込み、`Model.prototype.getRenderOrders()`という、ヒューリスティックを一切必要としない真の描画順APIを発見。これに置き換えて根本解決

**このプロセスで意識したこと**: 一度「動いた」ように見えた修正(手順3)を、新しい実データが出た時点で自ら疑い、感覚的な妥当性ではなく数学的な反例(三角形の重なり検証)で不十分さを証明してから、次の仮説へ進んだ。「推測で設計を書かない」という開発方針を、AIエージェントに対しても一貫して適用した結果。

### 2. マージ後の全体コードベース監査 — セキュリティ脆弱性の発見と是正

機能実装が一区切りついた時点で、コードベース全体(77ファイル)を7領域に分割し、レビュー専任のサブエージェントを並列起動して監査した。結果、重大度「高」以上を含む19件の不具合を検出:

- **フォルダ経由のモデル取り込みにシンボリックリンク対策が欠落**していることを発見。zip取り込み側には既にzip-slip対策が実装済みだったが、フォルダ取り込み側は同じ対策が漏れており、外部ファイルを指すシンボリックリンクを仕込んだフォルダを取り込ませることでローカルサーバー経由の任意ファイル読み取りが成立しうる状態だった
- ローカルサーバーの`error`イベントハンドラが起動後に外れており、ソケット異常でElectronのメインプロセスごとクラッシュしうる実装ミス
- HTTPレスポンスとソケット破棄の順序が逆で、エラー応答が実際にはクライアントに届いていなかったバグ

検出後は「修正→サブエージェントによる再監査」のループを4ラウンド回し、都度新たに見つかった論理バグ(例: 警告条件の判定漏れ)まで潰し込んで指摘0件を達成した。

## 開発プロセス — Claude Codeとの協働体制(ハーネスエンジニアリング)

本プロジェクトはアプリ自体の開発と並行して、「Claude Codeにどう実装させるか」の型化にも取り組んだ。

- **プロジェクト固有ルールの明文化**(`CLAUDE.md` + `.claude/rules/*.md`): 対称性チェック・正本管理・検証ルール・git運用をドキュメント化し、セッションが変わっても一貫した振る舞いを引き出す
- **対称性チェックの自動検知フック**: PostToolUseで直近の差分を見て、Live2D/スプライトセットのどちらか一方だけに触れる変更を検知し注意喚起する仕組みを自作。「フックは判断しない、最終判断は人が行う」という役割分担を明確にした
- **モデル使い分けの自動助言フック**: 依頼内容が「新規作成」か「既存修整」かを判定し、適切なモデル(新規=Opus、既存修整=Sonnet)を推奨する仕組み
- **reviewer専任サブエージェント**: 実装後に必ず読み取り専用のレビューエージェントを起動し、指摘が0件になるまで「修正→再チェック」を反復する運用を徹底
- **「動作確認済み」の自己申告禁止**: ElectronのGUIはサンドボックスから起動できないため、GUIを伴わない検証(オフスクリーン実行・モックサーバー・ライブラリの実測)に限定して確認し、実機確認が必要な項目は明示的にチェックリスト化してユーザーへ引き継いだ

このプロセスを通じて、AIエージェントの実装力を「無秩序に任せる」のではなく、検証可能なルールとチェックポイントで挟み込むことで、機能追加の速度と品質を両立させることを狙った。
